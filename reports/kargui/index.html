Rust の軽い GUI フレームワーク kargui の作成記録

前回の番外編では、Tauri・egui・GPUI の 3 つで同じ「タスク帳」を作って比べ、3 つにそれぞれ優れた所があると分かりました。そこで、それらの良い所を 1 つにまとめることを目指して、Rust の GUI フレームワーク「kargui」を AI（Claude）と作りました。名前は「軽い」「Rust」「GUI」から取っています。前回と同じ PC・同じ道具・同じ条件で測り、AI に書かせた時の書きやすさも調べました。

結論

起動の速さ・メモリ・CPU は、測った全部の項目で前回の 3 つより軽い値になりました。AI に書かせると、書く量は 4 つの中で最も少なく、仕様どおりに書けた度合いは Tauri が最も高く、kargui がその次でした。ただし kargui は部品も動く OS もまだ少なく、3 つと同じだけの機能を持った上での比べではありません。

  • 起動は 42 ms で、同じ回に測った前回の最良（egui の glow 版）の 344 ms の約 8 分の 1 です。1 万件を入れた時のメモリは 5.4 MB で、GPUI の 17.9 MB の 3 分の 1 以下です。
  • 何も起きていない間は CPU を使いません。GPU の無い PC でも、1 フレームの CPU 0.9 ms で 60 fps のスクロールを保ちます。
  • 日本語入力（確定の Enter で送らない、変換中は値を変えない、など）と、ナレーターでの読み上げを、作者が手で確かめました。
  • 公開している全部の関数と型に、動く例があります。API が変わったのに説明を直していないと、検査で落ちます。
  • 弱点もあります。Windows でしか動きません。部品はまだ少なく、ドロップダウンや「押せない状態」の部品がありません。作ってから日が浅く、使った人は作者と AI だけです。今後は実際のアプリを作りながら足りない物を調べ、足していきます。

ソースは github.com/dikmri/kargui で公開しています（MIT ライセンス）。crates.io にも 0.1 を出します。

なぜ作ったか

前回の比べでは、3 つにそれぞれ得意な所と、使う場面によっては気になる所がありました。

  • Tauri は画面を Web の技術で書けて作りやすく、GPU が無い PC でも滑らかに描けます。その分、起動のたびに WebView2 を立ち上げるので、起動に時間がかかり、メモリも多めに使います。
  • egui は書き方が簡単で、1 フレームの CPU も少なめです。既定の描き方（wgpu）は GPU のメモリを 170 MB ほど使い、日本語入力では変換中に値が変わりました。
  • GPUI は最も軽く、文字もくっきり描きます。一方で、型と寿命の書き方が難しく、説明も少なめでした。

3 つはどれも、kargui よりずっと多くの機能と利用者を支えている、完成度の高いフレームワークです。kargui は、その中から「egui の書きやすさ」「GPUI の軽さ」「Tauri の作りやすさと説明の多さ」を学び、1 つにまとめることを目指しました。目標の数字は「前回の 3 つの最良より、どの項目でも 3 割良い」にしました。比べる物差しをはっきりさせるためで、機能の多さまで含めた優劣を決めるものではありません。

kargui の作り

アプリの画面は、egui と同じ即時モードで書きます。状態は自分の構造体に持ち、view で毎回画面全体を書きます。

impl App for Counter {
    fn view(&mut self, ui: &mut Ui) {
        ui.row(|ui| {
            ui.label(format!("今の数: {}", self.count));
            if ui.button("1 足す").clicked() {
                self.count += 1;
            }
        });
    }
}

中の作りは、書き方とは別に軽さを優先しました。

  • 変わった所だけ描く: 毎回書いた画面を前の画面と比べ、変わった四角の範囲だけを描き直します。スクロールは今の絵をずらし、新しく見えた帯だけを描きます。
  • 既定は CPU で描く: GPU（Direct3D 11）の準備には 0.3 秒ほどかかります。変わった所だけ描くなら CPU でも十分速いので、既定は CPU で描き、GDI で窓へ写します。GPU で描く道も選べます。
  • OS とは直接つなぐ: 窓は Win32、文字は DirectWrite、日本語入力は IMM32、読み上げは AccessKit を、間の層を挟まずに使います。使う crate は全部で 26 個です（egui は 181 個）。
  • 2 回で決める配置: 下から大きさを測り、上から場所を決めます。大きさの分からない物の中央寄せや、残りの幅を分けることが 1 フレームで決まります。

測った結果

前回と同じ PC（Ryzen 5 3500・メモリ 64 GB・GeForce RTX 5060 Ti・Windows 11 Home）で、前回と同じ測定の道具を使いました。窓は 60 Hz のサブモニターに、前面に出さずに開きます。リリースビルドの設定も前回と同じです。比べる 3 つは、kargui と同じ回の中で測りました（2026 年 11 月 21 日）。値は中央値です。測った日が違うので、3 つの数字は前回のレポートの数字と少し違います。

「kargui」は既定の CPU で描く道、「kargui（GPU）」は Direct3D 11 で描く道です。斜線の棒は、そのフレームワークの既定ではない設定です。

起動

メモリ

CPU で描く道は GPU のメモリを使いません（0 MB）。前回の 3 つは、GPU のメモリを 15〜172 MB 使っていました。

スクロール

kargui は窓のあるモニターの速さ（60 Hz）に合わせて描き、前回の 2 つは 144 Hz で描いています。1 フレームの仕事は、アプリ自身の記録では約 0.58 ms でした。フレームの間隔の最長は 20.6 ms で、目標の「2 フレーム（33.3 ms）以内」に入りました。

低い性能の PC で

GPU を使えない条件では、GPUI は Windows の代わりの描き方（WARP）で 1 フレームに 68 ms かかり、Tauri は 5.2 ms かかりました。kargui は変わった所だけを CPU で描くので、0.9 ms で済みます。

日本語入力と読み上げ

入力欄は、Windows の日本語入力を最初から扱います。次の 5 つを、キー入力をまねる道具（Google 日本語入力）と作者の手で確かめました。

  1. 変換を確定する Enter では、送信になりません。
  2. 変換中の文字は入力欄の中に下線付きで出ますが、値は確定した時に変わります。絞り込みは、確定するまで走りません。
  3. 文節ごとに下線を引き、今変換している文節は太くします。
  4. 候補の窓は、打っている文字の真下に出ます。
  5. 変換の途中で別の欄を押しても、変換中の文字は元の欄に確定されます。

再変換（確定した文字を選んで変換し直す）は、まだ確かめられていません。作者の環境では変換キーが再変換に割り当たっておらず、Windows 標準の入力欄でも同じ操作で再変換が始まらなかったためです。

読み上げは、ナレーターで作者が確かめました。全部の部品に役割と名前があり、スライダーの値、一覧の行の「何件中何件目」、表の選んだ行が読まれます。名前の無い部品を作ると、記録に警告が出ます。

説明が古くならない仕組み

前回、GPUI は「物は良いのに説明が少なくて手を出しにくい」と感じました。kargui では、説明を書く決まりを検査にしています。

  • 公開している全部の関数と型に、説明と動く例があります。例は試験として実際に動かします。1 つでも欠けると検査で落ちます。
  • ガイドは日本語で書き、英語に訳しています。ガイドの中のコードも試験で動かします。
  • 各ページは、扱う API の形を覚えています。API の形が変わったのにページを見直していないと、検査で落ちます。日本語のページが変わったのに英語の訳を直していない時も落ちます。
  • AI 向けの索引（docs/llms.txt）は、ソースの説明から毎回作ります。手で 2 か所に書くことはありません。

AI に書かせて比べた

4 つのフレームワークそれぞれで、AI（Claude の Sonnet と Haiku）に同じ課題を 3 回ずつ出しました。課題はタスク帳の画面で、データの部分は 4 つとも共通の部品を使います。AI が読んでよいのは、そのフレームワークに付いてくる説明とソースだけです。組み立ては決まった台本で行い、毎回記録しました。各回の AI が開いたファイルも調べ、ほかの回や完成したタスク帳を見た回はありませんでした。出来上がったコードが仕様どおりかは、別の AI が 8 点満点の採点表で採点しました。

  • はっきり差が出たのは書く量です。kargui は egui の約半分、Tauri の約 3 分の 1 でした。kargui の AI（Sonnet）は説明を 1〜2 回読んだだけで書き終え、ツールを使った回数は 5〜7 回でした（ほかは 15〜28 回）。
  • GPUI では 6 回中 4 回、日本語入力の仕様を満たすために、公式の例を手本にして入力欄そのもの（約 700 行）を書いていました。
  • 日本語入力の 2 点（確定の Enter で足さない、変換中は絞り込まない）は、4 つとも全部の回で満点でした。

試験で見つけた kargui の弱点を直した

最初の 6 回では、kargui は仕様の採点で 4 つの中で最も低い 7.50 点でした。点を落とした所のうち 3 つは kargui の側の問題だったので直し、同じ課題で 6 回やり直しました。

  • 数の表示を描いた後で絞り込みを作り直す書き方をすると、操作の後に古い数が出ました。入力のあったフレームでは、画面が変わらなくなるまで view を回し直すようにしました。
  • 一覧の行の中にもう 1 つ行を入れて fill() を使うと、削除のボタンが行の右端へ行きませんでした。fill() を持つ入れ子の行は、自分も残りの幅を取るようにしました。
  • 明暗の切り替えを自分の値で持つと、OS が暗い設定の時にスイッチが見た目と逆を示しました。kargui 自身の明暗につながる dark_mode_switch を足しました。

直した後は 7.75 点になり、Sonnet の 3 回はすべて満点でした。残った減点は、課題のデータの部品の名前の表示（日本語で出る）など、kargui の外の物だけです。採点する AI は人によって厳しさが少し違うので、直す前と直した後の kargui は同じ採点役に頼みました。

作って分かったこと

  • 変わった所だけ描く仕組みは、絵で確かめる: スクロールで絵をずらすと、上に重なるつまみの古い絵もずれた先に残りました。文字の記録には絵の誤りが残らないので、「変わった所だけ描いた絵」と「全部描き直した絵」を 1 画素ずつ比べる試験を足しました。
  • 即時モードは、描いた後の値の変化に弱い: AI の試験で、描いた後に値を作り直す書き方で古い表示が出ました。フレームワークの側で回し直すと、書く人が順番を気にしなくて済みます。
  • 人の確かめを自動にする: 日本語入力の確かめは、前面の窓へキー入力をまねて送るので、作者が PC を使っている間は走らせられません。作者が 10 分席を外した時だけ走り、キーやマウスに触るとすぐ止まる道具を作りました。この PC はマウスに触れていなくても小さな揺れの入力が出続けていたので、手で動かした入力だけを数える形にしています。

弱点と、まだできていないこと

弱点

  • Windows 10/11 でしか動きません。
  • 部品と仕組みが少なめです。複数行の入力欄、ドロップダウン、押せない状態の部品、メニューやポップアップ、画像、複数の窓などがありません。足りない物の一覧は README の「Status and next steps」に載せ、実際のアプリを作りながら足していきます。
  • 作ってから日が浅く、使った人は作者と AI だけです。
  • 測ったのは 1 台の PC だけです。

まだできていないこと

  • 再変換の確かめ（上の「日本語入力と読み上げ」を参照）。
  • GPU で描く道（既定ではない）のスクロールで、0.2 秒止まる回がありました。
  • NVDA での読み上げは、まだ確かめていません。
  • macOS と Linux、説明のサイト。

ソースと測り直し方

ソース・ガイド・測定の台本・AI の試験の道具は、github.com/dikmri/kargui にあります。

cargo run --release -p taskbook-kargui -- --items 10000
cargo test --workspace --exclude kargui-spike
cargo run -p xtask -- check
bash tools/bench-phase3.sh

測定の台本は、前回のレポートの測定の道具（reports/rust-gui/bench/）を使います。このページのグラフは reports/kargui/bench/charts.mjs が reports/kargui/data/ の数字から作っています。
