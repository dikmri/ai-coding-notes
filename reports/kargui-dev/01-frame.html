kargui 開発レポート ・ 第 1 章

1 フレームの中で起きること

kargui のアプリは、画面の中身を毎フレーム書き直します。それでも軽く動くのは、前のフレームの配置を残しておき、変わった所だけを描くからです。この章では、マウスのクリックが届いてから画面に出るまでに、kargui の中で何が起きるかを順に追います。

この章で分かること

  • 1 回の入力で、アプリの view が最大 4 回呼ばれる理由
  • クリックがどの部品に当たったかを、前のフレームの配置で決める理由
  • 部品の名前（id）がソースの位置から作られることと、そこから来る注意点
  • 何も起きていない間に CPU を使わない仕組み

毎フレーム書き直す書き方

kargui のアプリは、画面の中身を 1 つの関数 view に書きます。ボタンを押したかどうかは、ボタンを作った所の戻り値で分かります。Dear ImGui や egui と同じ「即時モード」と呼ばれる書き方です。

struct Counter {
    n: u32,
}

impl App for Counter {
    fn view(&mut self, ui: &mut Ui) {
        ui.label(format!("押した回数: {}", self.n));
        if ui.button("押す").clicked() {
            self.n += 1;
        }
    }
}

この書き方では、画面の状態とアプリのデータを別々に持ちません。self.n を変えれば、次のフレームの画面に新しい数が出ます。部品を作って、後から中身を書き換える手順が要りません。

ただし、即時モードには弱点もあります。部品の大きさは、作り終えるまで分かりません。中央に寄せる・残りの幅を分けるといった並べ方は、1 回の呼び出しでは決められません。kargui は、view を呼ぶたびに画面の木（部品の親子の並び）を作り、木ができてから並べ方を決めます。即時モードの書きやすさと、残しておく木（保持モード）の並べ方を組み合わせた作りです。

入力が届いてから画面に出るまで

入力が届いたフレームでは、次の順に処理が進みます。

ビューを何回も呼ぶ理由

入力の回（3）では、押したボタンの clicked() が true を返し、アプリはデータを変えます。ところが、その時点の画面の木は、変える前のデータで作りかけです。そこで、入力を渡さずにもう 1 回呼び（4）、変えた後のデータで木を作り直します。

回し直し（5）は、アプリが「描いた後で値を作り直す」書き方をした時のための回です。たとえば一覧の件数を見出しに出し、その後で絞り込みを作り直すと、見出しは 1 回古い数を出します。kargui は 1 つ前の回と木を比べ、違っていればもう 1 回呼びます。木が同じになれば、そこで止めます。毎回違う木を作るアプリでも止まるように、回し直しは最大 2 回にしています。

やめた方がいい書き方: view の中で重い処理をする

入力のあったフレームでは、view が最大 4 回呼ばれます。フォルダーの中身を読む・大きなファイルを開くといった処理を view に直接書くと、1 回の入力でその処理が 4 回走ります。読んだ結果をアプリのデータに覚えておき、変わった時だけ読み直してください。見本のファイルの閲覧（examples/files）は、読んだフォルダーの中身を HashMap に覚えています。

クリックは前のフレームの配置で決める

マウスのボタンが押された時、kargui は「その位置にあった部品」を、前のフレームの配置から探します。今のフレームの配置はまだ作っていないうえに、利用者が見て押したのは前のフレームの画面だからです。

当たりの一覧は、描く処理（7）が部品を描きながら作ります。後から描いた物ほど上に重なるので、一覧の後ろから探せば、上に見えている部品が先に見つかります。メニューやダイアログのように重ねて出す物は最後に描くので、重なった下の部品にはクリックが届きません。

分かったこと: 当たりの一覧に載らない部品は、押しても気づかれない

ラベルや入れ物は押す対象ではないので、当たりの一覧に載りません。ドラッグ＆ドロップを足した時、ラベルの上から引っ張り始めると、窓がマウスの動きを kargui に渡していませんでした。窓は「押している部品がある時」だけ動きを渡していたからです。試験台は動きを直接送るので、この不具合は試験では出ませんでした。詳しくは第 5 章に書きました。

部品の名前はソースの位置から作る

毎フレーム作り直す部品が、前のフレームのどの部品と同じなのかを見分けるために、kargui は部品ごとに名前（id）を付けます。名前は次の 4 つから作ります。

部品の名前の材料
材料中身これで見分けられる物
親の名前中に入っている入れ物の名前別の入れ物の中の、同じ行の部品
ソースの位置部品を作る関数を呼んだファイル・行・列（#[track_caller]）ソースの別の場所で作った部品
呼んだ回数同じ位置を、このフレームで何回目に呼んだかループの中で作った部品
keyed の鍵アプリが渡した値（項目の id など）足す・消す・並べ替える一覧の項目

このおかげで、アプリは部品に名前を付けなくても書けます。入力欄の文字の位置や焦点は、名前が同じ限り次のフレームにも残ります。

やめた方がいい書き方: 消したり並べ替えたりする一覧を、回数だけで見分ける

ループの中の部品は「呼んだ回数」で見分けます。3 件の一覧から 1 件目を消すと、2 件目だった項目が 1 回目の名前を受け継ぎます。入力欄の文字の位置や焦点が、消した項目から隣の項目へ移って見えます。項目に id があるなら ui.keyed(id, |ui| ..) で囲むか、一覧なら show_keyed を使ってください。

変わった所だけを描く

描く処理（7）は、画面に描く物（四角・文字・画像）の一覧を作ります。既定の CPU の道は、前のフレームの一覧と比べ、違いのある範囲だけを塗り直して窓に写します。スクロールでは、窓の中の絵をずらし、新しく見えた帯だけを描きます。

入力も動く部品も無い間は、フレームを作りません。窓は OS のメッセージを待って止まります。そのため、何も起きていない間の CPU は 0 です。動く部品（進み具合の帯など）やツールチップを待つ間だけ、決めた時刻にタイマーで起きます。

タスク帳（1 万件）の 1 フレームで動くもの
場面view を呼ぶ回数描く範囲
何も起きていない0描かない（CPU 0）
ポインターが部品に乗った1色の変わった部品だけ
ボタンを押した2〜4変わった行と数の表示
一覧をスクロールした2〜4新しく見えた帯だけ

一覧は見えている行だけを作ります。1 万件でも、1 回の view で作る行は画面に入る数十行です。
