kargui 開発レポート ・ 第 4 章

CI を初めて回した日と 0.2.0

kargui のリポジトリには、送るたびに Windows・Linux・macOS で試験を走らせる仕組み（GitHub Actions）を用意していました。ただ、0.2 の作業を GitHub に送るまで、一度も走っていませんでした。初めて走った日、手元では全部通る試験が、Windows と Linux で落ちました。この章は、その原因をたどった記録と、0.2.0 を出すまでの手順です。

この章で分かること

  • 手元で通る試験が、CI で落ちる 2 つの典型（道具の版の違い・入っている物の違い）
  • 公開した版と比べて「使い方を壊す変更」を調べる方法
  • docs.rs で説明のリンクが切れていた理由と、もう起きないようにした仕組み

初めての CI の結果

初めての CI（16 件の commit をまとめて送った時）
OS結果落ちた所
macOS通ったなし（macOS で走らせたのはこれが初めて）
Windows落ちた説明の割合の検査が「説明 0/0」と数えて止まった
Linux落ちた組み立ての途中で、fontconfig が見つからずに止まった

どちらも、送った変更で壊れたのではありません。手元と CI の環境の違いが、初めての実行で表に出た物です。

Windows: 道具の版の違い

kargui には「公開している全部の項目に説明と動く例があるか」を数える検査があります。数えるのは rustdoc の --show-coverage で、結果の JSON を標準出力から読んでいました。

  1. 観測: CI では、検査が「説明 0/0」と数えた。手元では 479/479 だった。
  2. なぜ 0 か: CI の標準出力に、JSON が無かった。代わりに Generated output into "…/doc/kargui.json" の 1 行だけが出ていた。
  3. なぜ JSON が無いか: 手元の Rust は 1.95、CI は最新の 1.100 だった。1.100 の rustdoc は、この JSON を標準出力ではなくファイルに書く。

Rust 1.100 を手元に足して同じ命令を走らせ、この動きを確かめてから直しました。検査は、標準出力に置き場所が出ていればそのファイルを読み、出ていなければ標準出力を読みます。1.95 と 1.100 の両方で、479/479 と数えることを確かめました。

Linux: 入っている物の違い

  1. 観測: 組み立ての途中で yeslogic-fontconfig-sys が止まった。pkg-config が fontconfig を見つけられなかった。
  2. なぜ fontconfig が要るか: Linux の文字の道で使う parley の中の fontique が、OS のフォントを探すのに fontconfig を使う。組み立ての時に、その開発用のファイルが要る。
  3. なぜ手元では通ったか: 手元の試験に使う WSL2 には、開発用のファイル（libfontconfig1-dev）が前から入っていた。CI の素の ubuntu には入っていなかった。

CI で libfontconfig1-dev と pkg-config を入れるようにし、README の「Linux と macOS」の節にも、Linux で組み立てる時に要ると書きました。

やめた方がいい確かめ方: 手元で通ったから大丈夫、と考える

手元の道具の版と、手元に入っている物は、ほかの人の PC と同じではありません。CI は最新の stable の Rust と、何も入っていない OS で走ります。手元と CI の版の差は、作業の覚え書きに書いておき、CI と同じ版で確かめる命令も残しています（cargo +1.100.0 …）。

使い方を壊す変更を調べる

0.x の版では、0.1 から 0.2 に上げる時に使い方を変えてもかまいません。ただ、何が変わったかを書かないと、使う人が困ります。そこで、crates.io に出した 0.1.0 と今の公開の API を、道具で比べました。

  1. 0.1.0 を出した時の commit を、作業の場所を変えずに git archive で取り出す
  2. 両方の rustdoc の JSON（公開の項目の一覧）を作る
  3. 小さな台本で比べ、消えた物・形が変わった物・足された物を出す
  4. 足された物のうち、前からある型に足した値・欄・関数が、使い方を壊すかを調べる
0.1.0 と 0.2.0 の公開の API の違い
変わった所0.1.0 で書いたコードはCHANGELOG
消えた物0 件書く物なし
Key に #[non_exhaustive] と値 46 個全部のキーを並べた match が壊れる書いた
Options に欄 icon・min_size全部の欄を書いて作るコードが壊れる（..Options::new(..) なら壊れない）書いた
App に window・close_requested壊れない（どちらも既定の中身がある）書いた（壊れないことを）
Size::Fill・Size::Fixed変わっていない（台本の見かけの差）書く物なし
分かったこと: 比べる台本も、出た結果を確かめる

台本は最初、Size::Fill と Size::Fixed が「変わった」と出しました。中身を見ると、どちらも f32 を 1 つ持つだけで、0.1.0 と同じでした。rustdoc の JSON は、型の中の欄を番号で指します。その番号が作るたびに変わるので、番号ごと比べた台本が違うと判断していました。

説明のリンクが切れていた

0.2.0 の準備で説明を作り直すと、rustdoc が注意を 3 つ出しました。2 つは、説明の中のリンクの先（crate::Button）が見つからないという注意です。Button は kargui::ui の中にあり、kargui の直下にはありません。docs.rs の 0.1.0 の説明では、このリンクが切れて見えていました。

リンクを直したうえで、CI に「説明を注意なしで作れるか」の検査を足しました（RUSTDOCFLAGS=-D warnings）。注意が 1 つでも出れば、CI が落ちます。

0.2.0 を出すまでの分担

0.2.0 の公開の手順と分担
手順誰が
版の番号を 0.2.0 にし、CHANGELOG と README を直すAI
0.1.0 と比べて、使い方を壊す変更を調べるAI
Windows と Linux で試験と検査を通し、cargo publish --dry-run を通すAI
GitHub へ送り、CI が 3 つの OS で通るのを確かめるAI（作者が「送って」と言った時だけ）
crates.io に出す・版の印（タグ）を付ける作者

外へ出す操作（GitHub へ送る・crates.io に出す）は、作者が決めます。AI に任せた送る操作も、kargui の main を送る 1 行の命令だけを許可にしています。
